# Coding Agent Benchmark 知识大纲

这份大纲是后续 HTML 学习页的内容骨架，不是排行榜，也不是操作手册。
主问题：一道 coding agent 题从哪来、模型看见什么、能用什么工具、交回什么、怎样算做对。

阅读约定：

- **评测 harness**：出题方的沙箱、隐藏测试和打分程序。SWE-bench 的 `swebench.harness` 属于这一层。
- **Agent scaffold（解题脚手架）**：包住模型的循环、提示词和工具。SWE-agent、mini-swe-agent、OpenHands、Claude Code 属于这一层。
- 对外引用的分数是「模型 × scaffold × 资源预算 × 题目集 × 日期」，不是模型单变量。
- 带 `[核对]` 的数字或行为在不同论文、仓库和榜单之间不一致，生成 HTML 时再对官方页面，不要写成定论。

建议学习顺序：第 1 章建立地图 → 第 2 章分清两个 harness → 第 3 章把 SWE-bench 走完 → 第 4–5 章用对照题看另外两种技能 → 第 6 章学怎么读分数。

## 1. 总地图：三代题目

### 1.1 函数级代码生成

代表：HumanEval、MBPP。

- 问题：函数签名加自然语言说明，偶尔带几个例子。
- 模型看见：这一道函数的上下文，没有仓库。
- 工具：通常没有。一次采样，生成函数体。
- 提交物：一段代码。
- 验证：隐藏单元测试，看输出是否匹配。
- 现状：题目少、形式单一、公开多年，前沿模型上已经饱和，也容易被训练数据见过。HTML 里作为「为什么后来要换考法」的背景，不作为主线。

### 1.2 仓库级 issue resolving

代表：SWE-bench 及其家族。这是大纲的主线。

- 问题：真实 GitHub issue。代码库停在修复前的某个 commit。
- 模型看见：issue 文本，以及该 commit 上的仓库。看不见官方新增的测试。
- 工具：benchmark 不附送。工具由 scaffold 决定。
- 提交物：一份 unified diff（模型补丁）。
- 验证：在干净容器里打上补丁和隐藏测试，FAIL_TO_PASS 全部变绿，PASS_TO_PASS 保持绿色。
- 测的技能：读问题、在多文件仓库里定位、改对行为、不打坏原有测试。

### 1.3 把一台机器做到某个状态

代表：Terminal-Bench（现行任务格式在 Harbor 上）。

- 问题：自然语言指令，例如编译、配服务、把损坏的数据救回来。
- 模型看见：一个为这道题准备的容器，以及指令。
- 工具：进入容器后的 shell，具体命令面由接入的 agent 决定。
- 提交物：容器结束后的状态，以及任务声明要留下的文件。
- 验证：agent 退出后，另一套测试脚本写奖励；常见是隐藏 pytest，通过为 1，否则为 0。
- 测的技能：拆步骤、装依赖、从自己造成的失败里恢复。中途没有「已知失败测试」当完成定义。

### 1.4 赛题式程序，靠出题日期防背题

代表：LiveCodeBench。

- 问题：LeetCode、AtCoder、Codeforces 上持续新增的题，带题面和样例。
- 工具：通常没有仓库，也没有多步工具循环。
- 提交物：一份完整程序。
- 验证：隐藏测试加时间、内存限制。
- 额外场景：自我修复、执行代码、预测测试输出。不只考「写对一遍」。
- 抗污染办法：每题有发布日期。评一个新模型时，只取它训练截止日期之后的题。

### 1.5 首页对照表要用的列

后续每张卡片都填这 10 列，三道主线先填满，其余 benchmark 用短卡片。

1. 技能假设
2. 题目从哪来，会不会过期或被背下来
3. 解题时看得见什么
4. 评测时才出现什么
5. 环境 harness 做什么
6. 工具由谁提供
7. 合法提交物
8. 怎样算做对
9. 主指标，以及必须一起报告的条件
10. 主要失效：污染、测试过窄、flaky、scaffold 敏感

## 2. 先把两个 harness 拆开

这是整份材料的概念中心。不先讲这个，后面「SWE-bench 提供什么工具」会答错。

### 2.1 评测 harness 负责的事

- 把仓库或机器恢复到题目指定的起点。
- 把模型的产物放进去。
- 注入模型在解题时不该看见的测试或检查脚本。
- 跑检查，解析日志，写成通过或失败。
- 保证换一台机器，结果仍然可复现。手段通常是 Docker 镜像。

SWE-bench 官方文档把镜像分成三层，便于缓存：

| 层 | 内容 |
| --- | --- |
| Base | 语言和基础工具 |
| Environment | 某个仓库的依赖 |
| Instance | 这一道题的代码与配置 |

评测可以在本机 Docker 上跑，也可以放到 Modal，或用官方的云端入口。镜像缓存级别从「几乎不缓存」到「连题目镜像都留下」，换来的是磁盘占用。默认缓存 base 和 environment。`[核对]` 磁盘量级以当前文档为准：评测过程需要上百 GB 量级空闲空间；把每道题的镜像都留下会到 TB 量级。

### 2.2 Agent scaffold 负责的事

- 把 issue 和仓库交给模型。
- 决定模型每一步能发出什么动作：看文件、搜索、编辑、跑 bash，或根本不能行动。
- 把多轮轨迹收成评测 harness 认的提交物。对 SWE-bench 来说就是一份补丁。
- 决定步数、超时、失败后能不能重试、上下文满了怎么裁。

同一批题、同一个模型，换 scaffold，resolved 比例常有明显差距。二手综述里常见的幅度是十几个百分点。`[核对]` 这是经验观察，HTML 里写成「引用任何数字时必须写明 scaffold」，不要写成固定公式。

### 2.3 一张图里的三条箭头

```
出题方                         解题方                         打分方
issue + base commit    →    scaffold 调用模型        →    评测 harness
（测试先藏起来）              （工具在这一层）              （干净容器里注入测试）
```

模型不直接面对榜单。榜单面对的是「scaffold 交上来的补丁」或「agent 离开后的机器」。

## 3. SWE-bench 主线

### 3.1 它问的问题

给定一个真实仓库在 `base_commit` 的样子，以及对应的 GitHub issue 文本，交出一份补丁，使问题行为被修好，且无关功能的测试仍然通过。

做对不等于复现金补丁。金补丁是当时人类 PR 里、去掉测试改动之后的参考实现。另一份写法只要让规定的测试过渡成立，也算 resolved。官方 issue 讨论里明确过：测试和金补丁不能拿来生成答案；只允许使用 `base_commit` 的代码和 issue 描述。

题目从已合并、并且能关联到 issue 的 PR 里挖。原始全集集中在 12 个流行 Python 仓库。关联方式是在 PR 标题、正文和提交说明里找 “fixes / closes / resolves #编号” 这一类引用。

### 3.2 一道题的字段，以及谁能看见

HTML 第 2 屏用这张矩阵。列只有两列：解题时、评测时。

| 字段 | 是什么 | 解题时 | 评测时 |
| --- | --- | --- | --- |
| `instance_id` | 通常是 `owner__repo-PR号` | 可见 | 可见 |
| `repo` | GitHub 仓库 | 可见 | 可见 |
| `base_commit` | 修复 PR 落上去之前的提交 | 可见，作为代码起点 | 容器从这里开始 |
| `problem_statement` | issue 标题加正文。多条 issue 会拼在一起 | 可见，这是任务说明 | 不参与打分 |
| `hints_text` | PR 首次提交之前的评论，里面可能有解法暗示 | 数据集里有；论文主实验不用 | 不用 |
| `patch` | 金补丁，PR 中的非测试改动 | 不可见 | 仅在 `--predictions_path gold` 时当作待测补丁 |
| `test_patch` | PR 中新增或修改的测试 | 不可见 | 先打进仓库，再跑测试 |
| `FAIL_TO_PASS` | 打上测试后、打上修复前会失败，修复后应通过的测试名 | 不可见 | 决定「问题有没有被解决」 |
| `PASS_TO_PASS` | 修复前后都应该通过的测试名 | 不可见 | 决定「有没有打坏原有行为」 |
| `FAIL_TO_FAIL` / `PASS_TO_FAIL` | 其他过渡，用于附加统计 | 不可见 | 默认可选，不决定 resolved |

`problem_statement` 的收集范围是 issue 正文，加上 PR 首次提交之前、挂在这些 issue 上的评论。`hints_text` 来自更早的 PR 讨论。二者不要混。

### 3.3 这些测试名是怎么来的

造题时，出题方自己把仓库跑两遍（概念上）：

- 只有 `base_commit` 加上 `test_patch`：新测试失败，旧测试通过。
- 再加上金补丁：那些失败测试变绿，旧测试仍然通过。

从这两次日志里得到 `FAIL_TO_PASS` 和 `PASS_TO_PASS`。所以「标准答案」是一组测试状态过渡，不是一个字符串 diff。

过滤大致要求：PR 真的改了测试；仓库能安装、测试能跑；FAIL_TO_PASS 非空；行为稳定，不是时好时坏的 flaky。具体过滤脚本随版本变化，HTML 讲目的，不抄脚本。

### 3.4 评测 harness 的流程

官方模块是 `swebench.harness`。常用入口：

- 构建或拉取镜像
- `run_evaluation`：读一份预测文件，逐题打分
- 事后 `report`：只根据已经落下的日志重新汇总，不再开容器

预测文件是 JSONL。每行至少有 `instance_id` 和模型补丁（unified diff）。`predictions_path` 设为 `gold` 时，用参考补丁做自检，用来确认镜像和测试本身是通的。

单题打分顺序：

1. 准备这道题的容器，代码在 `base_commit`。
2. 把模型补丁放进容器，尝试 `git apply`。官方实现会换几种 apply 参数；一次失败可能弄脏工作区，所以会先把树恢复干净再试下一种。若命令退出码非零，还会用反向检查判断补丁是不是其实已经完整打上。
3. 打不上则该题失败，记为无法应用补丁，不再冒充「测试没过」。
4. 跑该仓库的评测脚本。脚本负责应用 `test_patch`、执行测试、留下日志。多模态题还会把数据集里另存的图片资源放回测试期望的路径，因为文本形式的 `test_patch` 带不走二进制基线。
5. 用该仓库的日志解析器，把每条测试标成通过、失败或错误。
6. 对照 `FAIL_TO_PASS` 与 `PASS_TO_PASS` 判 resolved。
7. 写出该题日志和本次 `run_id` 的汇总。

`[核对]` 模型补丁与 `test_patch` 的先后以当前 `run_evaluation` 为准。教学表述用上面的顺序：harness 先应用模型补丁，仓库评测脚本再应用测试补丁并跑测试。若两者改到同一处，顺序会影响能否应用。

判分规则（默认 PASS_AND_FAIL 这一类）：

- `FAIL_TO_PASS` 里每一个测试都要通过，问题才算被解决。
- `PASS_TO_PASS` 里每一个测试都要保持通过，才算没有回归。
- 两者同时成立，该题 resolved。
- 主指标是 resolved 的题目比例。

`[核对]` 日志里完全没有出现的测试名，在不同 grading 版本里可能算通过（代码注释里出现过 silent success）或算失败。HTML 不要写死。写成：缺失、错误、跳过是否等于失败，以所用 harness 版本的 `grading.py` 为准，并在报告里注明版本。

结果缓存按 `run_id` + `instance_id`，不看补丁内容。同一 run、同一题第二次会直接复用第一次的结果。换了一份补丁必须换 `run_id`。

其他运行事实，HTML 用侧栏而不是正文：

- 并行度 `max_workers` 过高会因抢资源变慢。文档建议低于大约 `min(0.75 * CPU 数, 24)`。
- 每题有超时。
- 平台建议 x86_64；arm64 支持是实验性的，Apple Silicon 上常见做法是把镜像命名空间留空、在本地构建。
- 日志分镜像构建和评测运行两类。汇总在该 `run_id` 的结果文件里。

### 3.5 解题时的工具：benchmark 不发，scaffold 发

用同一张表讲完。HTML 第 4 屏。

| 做法 | 模型能做什么 | 循环 | 用途 |
| --- | --- | --- | --- |
| 论文里的 Oracle 检索 | 直接看到金补丁改过的文件，一次写出补丁 | 无 | 上限参照，不是真实 agent |
| 论文里的 BM25 检索 | 用 issue 文本检索若干文件，一次写出补丁 | 无 | 早期非 agent 基线 |
| SWE-agent 的 ACI | 窗口看文件、有界搜索、按行编辑、编辑后做语法检查，不过则回滚；用 submit 交卷 | 多步 | 说明「给模型的电脑界面」本身会改变分数 |
| mini-swe-agent | 只有 bash。不依赖模型的 tool-calling 接口。每一步是一次独立命令执行，而不是一条一直活着的 shell 会话 | 多步 | 官方 Bash Only 榜：500 道 Verified，所有模型套同一个 scaffold，用来比模型 |
| Agentless | 先定位文件，再生成补丁，再用回归测试在候选补丁里挑 | 固定流水线 | 说明不一定要自由 ReAct 才能做这道题 |
| OpenHands 等 CodeAct | bash、Python、文件编辑，更接近通用编程 agent | 多步 | 研究系统和产品原型常用 |
| 厂商 agent | 各自的编辑、搜索、终端，有的还有浏览器和子 agent | 多步，预算各不相同 | 产品公告里的数字。不能和 Bash Only 直接横比 |

ACI 里后来被证明有用的界面决定，讲设计理由，不讲成「唯一正确工具集」：

- 文件查看一次给大约 100 行，并提供上下滚动和文件内搜索，避免整文件灌进上下文。
- 全库搜索只列出「哪些文件命中」，不把每处上下文都展开。
- 编辑命令带 linter；语法不合法就不要让这次编辑生效。
- 命令没有输出时，也要明确回报「成功且无输出」，避免模型把空白当成失败。

Bash Only 视图现在是 swebench.com 上 Verified 的默认比较方式：环境固定为 mini-swe-agent，比的是模型在同一界面下的表现。厂商如果用自己的 agent 再跑一遍 Verified，那是另一个实验。

解题时的合法能力边界：

- 可以读 `base_commit` 上已有的代码和测试，可以自己写临时测试，可以跑仓库里当时就存在的命令。
- 不可以拿到 `test_patch`、`FAIL_TO_PASS`、`PASS_TO_PASS` 和金补丁。官方隐藏测试是交卷之后才注入的。
- 因此「模型自己跑了仓库里的旧测试」不等于「它看见了判分测试」。很多判分测试是 PR 新加的，在 `base_commit` 上还不存在。

### 3.6 端到端时序

HTML 用三列，不要画成一张挤满的图。

**造题（离线，出题方做一次）**

1. 从仓库里找「issue 被某个 PR 关掉」的样本。
2. 拆成非测试改动（金补丁）和测试改动（`test_patch`）。
3. 做成可复现环境，在「只有测试」和「测试加金补丁」两种状态下跑测试。
4. 记下 FAIL_TO_PASS 与 PASS_TO_PASS。丢掉装不上、测不稳、测试与问题对不上的样本。

**解题（每个模型和 scaffold 做一次）**

1. 容器或工作区停在 `base_commit`。
2. 模型只拿到 `problem_statement` 和这个代码树。
3. scaffold 按自己的工具循环行动。
4. 抽出 `git diff`，写成预测 JSONL 的一行。

**打分（评测 harness，每个预测文件做一次）**

1. 换一个干净容器，仍然从 `base_commit` 开始。解题过程中的现场不能留下来。
2. 应用模型补丁；应用失败则该题未解决。
3. 应用 `test_patch` 并跑测试。
4. 解析日志，对照两组测试名。
5. 汇总 resolved 比例。报告里同时写数据集、scaffold、超时、日期、harness 版本。

第 2 步和第 3 步必须隔离。否则模型可以在现场把测试改掉，或留下解题时才安装的状态，评测就不再是在判那份补丁。

### 3.7 家族变体

同一类任务，不同的题库和访问策略。卡片字段沿用第 1.5 节。数字全部标 `[核对]`，下面给的是 2026-09 查阅官方页面和论文时的量级，生成 HTML 前以 swebench.com、对应论文和数据集卡为准。

| 名称 | 规模（核对） | 和 Full 的差别 | 教学重点 |
| --- | --- | --- | --- |
| SWE-bench Full | 2294 | 12 个 Python 仓库的原始测试集 | 任务定义的出处 |
| Lite | 300 | 更便宜的子集，方便改 scaffold 时迭代 | 开发用，不是头条 |
| Verified | 500 | 人工过滤后的子集。问题陈述或 FAIL_TO_PASS 被任一标注者判为有严重问题时剔除 | 现在最常被引用的工程分数 |
| Bash Only | 500，题与 Verified 相同 | 强制同一个 mini-swe-agent | 把 scaffold 从比较里拿掉 |
| Multimodal | 榜上写 517；FAQ 又写开发集 100，测试评测走 API | issue 带截图和界面信息；评测要还原图片资源 | 视觉信息也是问题陈述的一部分 |
| Multilingual | 300，42 个仓库，9 种语言 | 官方仓库上的多语言切片 | 不要和 Multi-SWE-bench 混名 |
| SWE-bench Pro | 1865 = 公开 731 + 保留 858 + 商业 276；41 个仓库 | 长程、改动更大。公开与保留集偏向强 copyleft 仓库以降低训练污染；商业集是初创公司私有库，只公布分数 | 问题陈述经人改写，另有需求列表和接口说明，但不规定怎么实现 |
| SWE-bench Live | 滚动更新。论文样本 1319、93 个仓库；之后按月往 full 加题，lite / verified 切分保持冻结 | 2024 之后的新 issue；用 RepoLaunch 自动做 Docker 环境 | 用新鲜题对抗背题。另有多语言和 Windows 切分 |
| Multi-SWE-bench | 论文摘要 2132、8 种语言；仓库说明又见 1632、7 种语言，外加 mini | 专家标注、难度分层；评测同样是容器里打补丁、看测试过渡 | 跨语言、跨文件。Python 是否计入视版本而定 |

Pro 的单题比原始 SWE-bench 多两样解题时可见的材料：人写的需求列表，以及可选的接口说明。平均改动在论文报告里大约是一百行、四个文件。`[核对]` 精确均值以论文为准。验证仍然是人工看过的 FAIL_TO_PASS / PASS_TO_PASS，在干净容器里跑。公开集的任务可以落成 Harbor 目录：指令、环境、测试脚本、金解。

Verified 存在的原因要单独讲，否则读者会以为 500 只是随机抽样。标注者在看两类缺陷：问题陈述不足以决定该改什么，以及测试太窄、太宽或和 issue 对不上。过滤偏严：三名标注者里有一人认为严重，样本就会被拿掉。

Live 的造题比原始 SWE-bench 多一个自动环境阶段：找安装说明、选基础镜像、装依赖、构建、跑通测试，再多次重跑以确认 FAIL_TO_PASS 稳定。教学点是「可执行环境」本身是 benchmark 的成本中心，不是附赠品。

### 3.8 原始论文设定和后来的 agent 设定

HTML 用一个时间注脚，避免读者以为 SWE-bench 一发布就是今天的 agent 榜。

- 2023 论文的主实验是检索加一次生成，不是多步工具循环。Oracle 检索把金补丁碰到的文件直接给模型，BM25 则是真实检索。
- 2024 起，SWE-agent 这一类多步 scaffold 成为主要报告方式，评测也改为全容器。
- 再往后，榜单分裂成「固定 bash scaffold 比模型」和「各家 agent 比产品」。

## 4. Terminal-Bench：对照，不是 SWE-bench 的难版

### 4.1 问的是另一件事

SWE-bench 给一个静止的仓库和一个已知的失败定义，请模型交出补丁。
Terminal-Bench 给一个会被动过的环境，请 agent 自己拆目标、执行、并在自己弄坏现场之后继续。检查发生在 agent 宣布结束之后。

规模 `[核对]`：2.0 / 2.1 是几十道到约 89 道人工编写并核对过的题，论文进入 ICLR 2026。以官方仓库为准。题量小，所以单题权重高，也更要报告方差和重复次数。

### 4.2 一道题的目录

现行格式是 Harbor 任务。旧 Terminal-Bench 把指令塞在 `task.yaml`、用 `run-tests.sh` 的退出码加仓库里的解析器打分。Harbor 改成下面这样：

| 路径 | 作用 | 谁能看见 |
| --- | --- | --- |
| `instruction.md` | 给 agent 的自然语言任务 | 解题时可见 |
| `task.toml` | 超时、资源、要保留的 artifacts | 运行配置 |
| `environment/` | Dockerfile 或 compose，agent 的工作容器 | 解题时生活在这里 |
| `tests/test.sh` | 验证脚本。应把奖励写到 `/logs/verifier/reward.txt` 或 `reward.json` | 解题时不可见 |
| `tests/` 里的其余文件 | pytest 等 | 不可见。参考答案和期望数据放这里，不要放进 environment |
| `solution/solve.sh` | 参考解，给 oracle 跑通检查 | 不可见 |

较新的约定里，验证器可以在另一个容器里跑，并且只读取任务声明导出的 artifacts、烤进验证镜像的文件，或 compose 里声明的持久边车。这样 agent 无法在自己的容器里改掉测试。

奖励可以是 0/1，也可以是浮点，或一个多指标 JSON。主榜常用二元通过。

### 4.3 工具和分数单位

- 评测框架提供容器和验证时机，不规定模型的编辑器。
- 实际工具取决于接入的 agent。中立 scaffold（如 Terminus）和厂商 CLI 不是同一个界面。
- 榜单单位明确是 agent + 模型。同一模型换 scaffold，或只换机器资源限制，分数都会动。`[核对]` 公开讨论里出现过数个百分点到大约十分的差距，HTML 只保留「必须同时报告 harness 和资源」，不引用未经原始报告核对的具体百分点。

### 4.4 和 SWE-bench 的差异（第 6 屏的整张表）

| | SWE-bench | Terminal-Bench |
| --- | --- | --- |
| 起点 | 真实仓库的一个 commit | 为题目构建的容器 |
| 完成定义 | 隐藏测试的状态过渡 | 指令是否被做完，由验证脚本给奖励 |
| 提交物 | unified diff | 结束时的工作区 / 声明的 artifacts |
| 测试何时注入 | 补丁应用之后，由评测脚本打入 `test_patch` | agent 结束后，验证脚本才运行 |
| 中途反馈 | 可以跑 `base_commit` 上本来就有的测试；官方新测试还不在树上 | 可以看自己命令的输出；看不到验证器 |
| 环境会不会被自己搞坏 | 最终只认补丁，现场会被丢掉 | 最终就认这台被改过的机器 |
| 典型失败 | 定位错、补丁打不上、修了问题但回归 | 步骤顺序错、依赖没装上、进程没起来、把环境修到更坏 |
| 报告单位 | 常写成模型名，实际含 scaffold | 必须写成 agent + 模型 |

## 5. LiveCodeBench：对照里的第三极

短章节。目的是让读者看见「代码能力」至少有三种考法。

- 来源：LeetCode、AtCoder、Codeforces 的定期比赛。题面经过大量人类选手检验。
- 解题输入：自然语言题面、样例输入输出。没有仓库历史。
- 工具：标准设定是生成程序，不是在容器里自由施展多步工具。若某次实验加了 agent，那是另一套协议，必须另报。
- 验证：隐藏测试。判定器沿 APPS 的 checker 改过，处理原先没覆盖的边界。有时间与内存限制。另有精简测试集用来加速，和全量测试集要分开报。
- 四个场景：生成代码、自我修复、执行并得到输出、预测某组测试的输出。生成分高不代表后三个也高。
- 抗污染：题目带 `contest_date`。按模型训练截止日期切窗口。论文用这个现象说明旧题分数会被抬高。
- 和 SWE-bench 的差别：没有跨文件工程上下文，判定是输入输出，不是仓库里的回归测试；新鲜度靠持续收新题，而不是靠把旧 PR 藏起来。

## 7. 读分清单

HTML 最后一屏，做成可勾选的清单。

引用一个百分数之前，页面上要能指到这六件事：

1. 题目集的真名和规模：Verified、Pro 公开集、Pro 商业集、Live 的哪一个月，不能都叫 SWE-bench。
2. scaffold 的真名和配置：Bash Only、厂商 CLI、或论文里的 BM25 一次生成。
3. 提交次数与预算：是一次交卷，还是内部重试、多数投票、更长超时。
4. 日期和 harness 版本：缓存规则、日志解析和镜像都在变。
5. 指标定义：resolved 是否同时要求 PASS_TO_PASS；缺失测试怎么计。
6. 比较对象是不是同一种单位：模型、还是 agent + 模型。

常见误读，每条配一句正确说法：

- 「模型 A 的 SWE-bench 是 70%」：没有变体名和 scaffold，就无法和另一则 70% 比较。
- 「Verified 已经很高，所以工程能力解决了」：题目与金补丁长期公开，存在背题和过拟合空间；Pro、Live、时间切分就是针对这件事。
- 「Terminal-Bench 更高说明比 SWE-bench 更强」：考的技能不同，分母和 harness 敏感度也不同。
- 「agent 跑过测试所以它看见了判分标准」：它能跑的是起点上就存在的测试；判分用的新测试在交卷后注入。
- 「和金补丁不一样所以算错」：判的是测试过渡，不是 diff 相等。

## 8. 术语

| 词 | 人话 |
| --- | --- |
| resolved | 规定的失败测试都变绿，且规定的原有测试仍然绿 |
| FAIL_TO_PASS | 这道题专门用来证明「问题被修好了」的测试 |
| PASS_TO_PASS | 用来证明「没把别的东西改坏」的测试 |
| test_patch | 人类 PR 里的测试改动，解题时隐藏，打分时注入 |
| gold patch | 人类 PR 里的非测试改动，是参考实现，不是唯一正确实现 |
| base_commit | 修复发生之前的仓库快照 |
| 评测 harness | 干净环境、注入测试、解析日志的程序 |
| scaffold | 模型外面的循环和工具 |
| ACI | Agent-Computer Interface，专门为模型设计的那套看文件、搜索、编辑动作 |
| Oracle 检索 | 直接把金补丁会改到的文件给模型，用来估计检索不是瓶颈时的上限 |
| 污染 | 题目或答案已经出现在训练数据里，分数不再表示遇到新问题的能力 |
| flaky | 同一份代码重复跑测试，结果不稳定。这样的题不能用来打分 |
| reward.txt | Terminal-Bench / Harbor 里验证脚本写下的分数文件 |

## 10. 下一轮生成 HTML 时的范围

做一页可本地打开的学习页，覆盖第 0–8 节。第 6 节的短卡片先放已在本大纲写明的对比关系，规模数字遵循第 9 节。

视觉：

- 深色阅读页，适合长文。三张主线用同一卡片组件。
- 可见性矩阵用切换，不把两列并排挤在手机上。
- 时序用三步，移动端改为纵向。
- 文案用本大纲的句子，不另起一套比喻，不放 lorem，不放假排行榜。
